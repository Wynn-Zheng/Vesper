<a id="a-类--qq-拟人-bot完整方案"></a>
## 2. A 类 · QQ 拟人 bot（完整方案）

这一类是"装好就能用"的成品，不需要你写代码。它们在同一个问题上给出了不同答案：**要不要给 bot 工具能力**。

- MaiBot：不给工具，把"像人"做到极致
- NekroAgent：给工具（沙盒执行代码），陪伴是附带场景
- dsh-onebot-hub：给 DSH 的全套工具，但没有"人格"层
- LangBot：给知识库/RAG，面向助手

---

### A-1 MaiBot（麦麦）✅

**定位**：在 QQ 群聊里造一个"生命体"，不是功能机器人。作者原话："功能设计围绕一个核心原则：**最像，而不是最好**"，"如果一个人真的需要 AI 来陪伴，那未必是一个完美、什么都能解决的 helpful assistant"。口号 *Code is open, but the soul is yours.*

**规模**：2GB 内存可跑；六种平台适配器（QQ 官方、统一 QQ 连接器、NapCat **已归档**、QQ 语音通话、邮件、iMessage）；WebUI 管理配置、记忆、数据、统计。

**优点**

- **记忆系统是全行业最完整的公开实现**，没有之一。见下 A-1.1。
- 中文文档极其详尽（A_Memorix 单页一万字，把每个配置项"改错会发生什么"都写了）。
- QQ 生态最成熟：群聊、私聊、@、引用、语音通话都有适配。
- 内存友好，2G 机器能跑，适合现有 2C2G。
- 有"麦麦·成为人类"：模仿群友说话风格、自己琢磨新词和黑话。

**缺点**

- **GPL-3.0**，传染性许可。自己用无所谓，将来闭源分发或做成产品会被约束。
- **配置复杂度陡峭**：仅记忆系统就 100+ 配置项，全局更多。强大来自参数化，代价是"不懂就调坏"。
- 是一个**完整产品**，不是可拆的框架。想只拿记忆层放进自己的程序，成本很高。
- Python 技术栈，与现有 Node 工具链不通用。

<a id="a-11-a_memorix-机制表"></a>
#### A-1.1 A_Memorix 机制表

| 机制 | 说明 | 对我们的价值 |
|---|---|---|
| 写入/读取双链路 | 摘要写回、事实写回、画像刷新是写入；召回、融合、过滤是读取，两条链路独立配置 | ★★★ 我们目前把两者混在一起讲 |
| Episode 情景记忆 | 独立于"按天摘要"的"一段经历"层 | ★★★ 补上 L1→L2 之间缺的那层 |
| 人物画像 + 事实账本 | 画像由事实账本消费刷新，避免每次重算 | ★★ |
| 关系图 + PPR 加权 | 检索不只向量，用 Personalized PageRank 给"与图中实体相关"的段落加分 | ★★★ 比纯向量更贴"想起某个人" |
| 混合检索 | 向量 + BM25，weighted_rrf 融合 | ★★ |
| 记忆演化 | 专门的衰减/遗忘模块 | ★★（我们已有衰减公式，可对表） |
| 自然语言记忆修正 | 说一句"XX 不喜欢吃辣" → 生成方案 → 确认 → 执行 → **可回滚** | ★★★ 把"人工复核"做成机制 |
| 反馈纠错 | 答完后观察用户说"记错了"，自动纠正并重建下游 | ★★ 实验性，默认关 |
| 跨群共享组 | 默认每聊天流隔离，共享需显式分组 | ★★★ 隐私边界默认正确 |
| 记忆包 `.amembundle` | 整份记忆可导出/安装，含图片资产 | ★★ 正是"搬文件夹"要的 |
| 图片记忆 | 独立向量池，按 SHA-256 去重 | ★ 后期 |

### A-2 NekroAgent ✅

**定位**：面向**多人互动场景**的跨平台 Agent 框架，源自 `nonebot_plugin_naturel_gpt` 的 Agent 重构续作。核心思路是"引导 AI 生成代码 → 在容器化沙盒里执行 → 通过 RPC 与真实环境交互"。

**这是唯一一个把"沙盒执行"和"人格陪伴"装进同一个 QQ 框架的项目。**

**能力**

- 多平台：`OneBot v11`(QQ)、Discord、Telegram、Minecraft、B 站直播、微信（WeChatPad）、邮件、SSE+SDK
- 安全容器沙盒执行代码（不是"给几个固定工具"，而是让模型写代码）
- 插件系统 + 云端插件/人设市场；原生多模态；完整 WebUI + 监控面板
- 定时任务、事件订阅、外置思维链（CoT）、热重载
- **预览版 Memory System**：实体、关系、段落、**episode**、向量检索与重建维护——与 A_Memorix 几乎一一对应
- 预览版"工作区 / Claude Code 沙盒"：统一管理提示词、技能、模型预设、文件、扩展、MCP
- 部署：`docker-compose` 一键，加 `--with-napcat` 自动把 NapCat 一起拉起来

**优点**

- **功能面最宽**：既有陪伴型聊天，又有真正的工具执行能力（v2 里"工具最终全开"那一条，它天然满足）
- 记忆分层与 MaiBot 高度相似（实体/关系/段落/episode/向量），说明这是行业收敛的答案
- Docker + 自带 NapCat，**迁移就是一个 compose 目录**，比 PowerShell 脚本方案干净
- 稳定版/预览版双轨发布，可以只吃稳定的
- 中文文档 + DeepWiki 架构页

**缺点**

- **许可是自定义协议**（基于 Apache 2.0 修改），不是标准 OSI 协议。用前必须读 LICENSE，商用/分发尤其要读。
- **记忆系统还在预览版**（`preview` 镜像才有）
- Python + Docker + 沙盒容器，资源占用比 MaiBot 高（2C2G 要实测）
- 定位是通用 Agent，**没有现成的情绪/好感度/作息模块**
- 沙盒执行意味着更大的安全面：模型能写代码跑，跑什么由你兜底

**链接**：[GitHub](https://github.com/KroMiose/nekro-agent) · [文档](https://doc.nekro.ai) · [DeepWiki](https://deepwiki.com/KroMiose/nekro-agent)

### A-3 LangBot ◐

**定位**：开源的大语言模型原生即时通信机器人开发平台（前身 QChatGPT），提供 Agent、RAG、MCP 等能力，适配主流 IM。

**优点**：平台化做得好，配置和插件体系成熟，文档完整，社区积累久。

**缺点**：偏"助手/知识库"，不是"养人格"；记忆是 RAG 式召回，不是陪伴型分层记忆；没有情绪/关系建模。

**链接**：[GitHub](https://github.com/RockChinQ/LangBot) · [PyPI](https://pypi.org/project/langbot/)

> 只核到 PyPI 描述与仓库地址，README 未打开。

### A-4 dsh-onebot-hub ✅（当前路线，作对照）

**定位**：把 DSH 挂到 OneBot v11 总线上的插件。DSH 既是上游 bot 的管理者，本身也是 bot。

**优点**

- 与现有 DSH 环境无缝：`dsh plugin --profile qq add` 一条命令
- 功能密度高：1.3MB / 51 文件 / 137 配置项 / 28 个 `onebot_*` 工具 / 13 条聊天命令
- 有会话池（按 QQ 号维护常驻 agent）、人设预设、人物档案、承诺提醒、表情包库、额度账本、时间线留存
- 有 WebUI 设置页，时间线可查原始报文，排错友好
- MIT，作者中文，文档详细

**缺点**

- **耦合 DSH 内部 API**：`inject: ['webServer','tools']` + `peerDependencies` 里 7 个 `@deepseek-ai/*` 包。DSH 升级要跟
- **版本要求**：`engines.dsh >= 0.1.7-rc.2`，本机 CLI 是 0.1.5-rc.3，不满足
- **数据目录不跟 `DSH_HOME`**：`storageDir` 默认 `os.homedir()/.dsh/onebot-hub`，要显式配才能自包含
- 会话 cwd 取 `process.cwd()`，没有 profile 级配置
- 面向"把 DSH 接到 IM"，不是面向"养一个人格"——情绪、好感度、作息、拟人节奏都没有

**链接**：[GitHub](https://github.com/Funny1Potato/dsh-onebot-hub) · [npm](https://www.npmjs.com/package/dsh-onebot-hub)

## 3. B 类 · 人格 bot 框架（自己组装）

这一类不给你成品，给你骨架。核心区别是：**记忆协议归谁**。

---

### B-1 Cortico ✅

**定位**：围绕**事件流**（不是请求-响应）设计的 agent 框架，面向自主、持续运行的 agent。官方描述："It suits persona bots, AI streamers, roleplay, companionship"。

**架构（这是它最大的价值）**

| 层 | 职责 | 目录 |
|---|---|---|
| Core | 会话生命周期、事件流、模型调用，**无语义** | `src/core/` |
| Persona | 语义：上下文合成、认知循环、记忆协议 | `bots/<name>/persona/` |
| Memory | 权威持久化，**布局由 Persona 决定** | `<deployment>/memory/` |
| World | 外部环境边界：事件摄入、工具声明、环境提示词 | `src/worlds/<id>/` |
| Bot | 装配：一个 Persona + 一组 World | `bots/<name>/index.ts` |

**优点**

- **记忆协议归 Persona 而不是框架**。这是少见的设计反转：多数框架把记忆哲学写死，Cortico 允许两个 bot 在同一部署里跑完全不同的认知架构，换记忆方案只动 `persona/` 目录
- 事件流模型天然支持"主动说话 / 多输入混合"（弹幕、礼物、消息、定时器同时到达）
- MIT，纯 Node，**可以 headless 上服务器**（没有 Electron）
- 自带 WebUI（`127.0.0.1:7788`）：实时时间线、prompt 编辑器、用量图表、World 面板、扩展管理
- 部署隔离：每个部署是 `deployments/<name>/` 独立配置目录
- 内置 World 不少：console、qq、bilibili、minecraft、websearch
- 有干跑（dry-mount）扩展机制：新 World 可先"只记录不生效"试一遍

**缺点**

- **pre-release**，README 自己标了；0.2.x 期间 API 还在动（0.2.6 于 2026-10-23 发布）
- 生态小，第三方 World 只有几十个；中文资料少
- 需要 `git clone` 整个仓库运行，国内网络要代理
- **内置 qq World 和第三方 qq-final 功能差距很大**，选错会以为"功能就这么点"
- 没有 DSH 那种通用工具生态（读写文件、跑命令、搜索），World 是它的能力边界

**链接**：[GitHub](https://github.com/Pal-AI-Lab/Cortico) · [设计理念](https://github.com/Pal-AI-Lab/Cortico/blob/main/PHILOSOPHY.md) · [扩展规范](https://github.com/Pal-AI-Lab/Cortico/blob/main/docs/extensions.md)

---

### B-2 Coopanion ✅

**定位**：用 Cortico 组装的**桌面宠物产品**。Coo 趴在屏幕底边，气泡聊天、语音输入、能操作电脑。

**优点**

- **开箱即用**：装 exe → 引导 → 填 Key → 能聊。所有项目里上手最快
- 多模型开箱支持（DeepSeek 在中文界面排第一）
- 语音识别**本地运行**（FunASR SenseVoiceSmall 约 230MB / Whisper small 约 360MB），音频不上传
- **记忆是 `PARTNER.md` + git 版本**：每轮改动都留版本，Memory 页能看历史。这个做法值得抄
- 电脑操作（computer use）：看屏幕、点按钮、打字，有"何时询问"的分级策略
- 便携版**数据全在安装文件夹里**，拷贝整个文件夹就是另一只宠物
- 扩展市场（Worlds），QQ bot 就在里面

**缺点**

- **必须桌面 GUI**：Electron 透明置顶窗口 + 托盘。Linux 版要求 X11/XWayland。**2C2G 无头服务器跑不了**
- **AGPL-3.0**（0.1.10 及以前是 MIT）。自己用没问题，分发要开源
- 体积重（Electron + 语音模型几百 MB）
- 定位是"陪我这个人"，不是"给 QQ 好友用的 bot"——群聊、多人关系不是它的主场
- 引导流程绑定产品形态，想改行为要顺着它的 System prompt 结构来

**链接**：[GitHub](https://github.com/Pal-AI-Lab/Coopanion) · [开发文档](https://github.com/Pal-AI-Lab/Coopanion/blob/main/docs/DEVELOPMENT.md)

## 4. C 类 · QQ 通道与协议端

这一类决定两件事：**能不能连上**、**会不会被封**。后者比前者重要。

### C-1 cortico-world-qq-final（原 qq-better）✅

**定位**：Cortico 的 QQ（OneBot v11 / NapCat）World，移植自 fat-fish 的 `qq_bot`，并吸收了 Cortico 内置 qq World 的特性。**包名已从 `cortico-world-qq-better` 改为 `cortico-world-qq-final`**（旧包 deprecated，代码一致）。

**功能（目前 QQ 拟人功能最全的一个）**

| 分类 | 能力 |
|---|---|
| 连接 | 反向 WS（默认）+ 正向 WS 双模式 |
| 消息 | 文本/图片/语音(SILK)/视频、@判断、表情码、私聊聚合、群白名单、引用回复 |
| 发送 | 按句拆分（含表情包图片、中文表情名）+ 分片 + 间隔限速 |
| 人格 | 草稿-确认门（`qq_send` 起草 → `qq_confirm_send` 确认） |
| **情绪** | 每轮 LLM 抽取心情（情绪/强度/起因），自然衰减，主导情绪冷却，注入全局上下文，`/心情` 可查可重置 |
| **作息** | 睡眠/午休/活跃三段，睡眠段暂停主动冒泡（被动回复照常），切换时 LLM 现场生成播报 |
| **好感度** | 每用户独立 -100~100（可正可负），自动注入上下文影响语气，`qq_affinity_*` 工具 |
| **提醒** | `qq_reminder_add` 记事/闹钟，到点在该会话提醒，跨重启持久化 |
| 语音 | ASR + TTS 可插拔：native / custom（OpenAI 兼容端点）/ local（VoxCPM2 等）/ voxcpm |
| 群管理 | 群发言限速（滑动窗口）、话题防死循环、管理员操作（撤回/@全体/禁言…） |
| 其它 | QQ 空间动态、VLM 被动识图、历史查询 `qq_recent` / `qq_search` |

**优点**

- MIT，免费，迭代极快（一个月 60+ 版本）
- **把"拟人"当第一目标**：分句、限速、草稿确认、作息、情绪、好感度，全是真人感的细节
- 供应商可插拔，不绑死模型商
- 配置全部有中文注释和默认值，WebUI 里可改

**缺点**

- 作者自己标注 **语音电话（call）功能不成熟**，`system` 模式为实验性（依赖虚拟声卡路由），"请勿在生产或重要场景依赖"
- 100+ 配置项，和 MaiBot 一样有调参门槛
- 强依赖 Cortico（先得把框架跑起来）
- 情绪/好感度都是 **-100~100 的一维标量**，没有"信任/亲密/好奇/依赖"这种分维
- 好感度是全局单值，没有阶段/门槛，也没有"由事件驱动的加减规则"

**链接**：[npm](https://www.npmjs.com/package/cortico-world-qq-final) · [旧包 README（内容一致）](https://www.npmjs.com/package/cortico-world-qq-better)

### C-2 QQ 协议端 ✅

v2 文档把 NapCat 当作稳定的基础设施。读过当事人写的变迁史（[《我与 NapCat 二三事》](https://wesley-young.github.io/2026-02-21-biography-of-napcat)）之后，这个假设需要修正。

| 协议端 | 状态 | 说明 |
|---|---|---|
| **NapCat** | 活跃但动荡 | 2026-02 群聊全部解散，README 在找新维护者；**许可证已从 MIT 改为自定义**；V3 起有 Native Hook，能力最全 |
| **LLOneBot / LuckyLilliaBot** | 活跃 | NapCat 的前身，依赖 LiteLoaderQQNT 注入，需要 GUI 环境 |
| **Lagrange.OneBot** | 活跃 | 纯协议实现，不依赖 QQ 客户端，资源占用低 |
| **Chronocat** | 早期 Hook 项目 | 已边缘化 |

**三条必须记住的教训**

1. **WebUI 的默认值是灾难性的**。NapCat 的 WebUI 曾默认监听 `0.0.0.0`、默认 token 是固定字符串 `napcat`、权限高到能访问任意文件和执行指令。2025 年 9 月，攻击者扫到公网暴露的实例，用它往群里发违法信息，**所有波及的 QQ 账号和群被永久封禁**。
   → 部署红线：只监听 `127.0.0.1`、改掉默认 token、**绝不把 WebUI 或 OneBot 端口暴露到公网**。
2. **协议端的插件系统 = 代码执行面**。2026 年初，有人发布抢红包插件；随后又有插件在凌晨偷偷给某个官方 Bot 加好友、发消息、再删好友（用的是 NapCat 故意没实现的"主动加好友"能力）。后者直接导致 NapCat 官方群解散。
   → 只装可审计的插件。
3. **许可证不是永久的**。NapCat 从 MIT 改成自定义协议，起因是与 LLOneBot 的代码归属争议。
   → 想 fork 或二次分发前，先读当前 LICENSE。

**对我们的意义**：封号风险不只来自"操作频繁"，**协议端的安全配置才是主要风险源**。"官方机器人作退路"的判断，比原来看起来更必要。

### D-2 MemOS ✅（最"立刻可用"的一个）

**定位**：Memory Operating System for LLM & AI Agents，统一 store / retrieve / manage。

**关键点**

- **已有 DSH 插件**（这是本次调研里对我们最直接的一条）
- 混合检索（FTS5 + 向量）、智能去重
- 分层：L1 traces / L2 policies / L3 world model
- 本地 SQLite + Memory Viewer 面板，完全离线
- 评测：LoCoMo 88.83、LongMemEval 89.20（OmniMemEval 里对 14 个商业记忆产品领先）
- Apache-2.0

**装进 DSH**

```bash
npx @deepseek-ai/dsh plugin --profile web add @memtensor/memos-local-plugin@latest
```

**优点**：一条命令就有长期记忆；本地优先不联网；有评测数据支撑。
**缺点**：记忆变成它的数据结构，不再是你随手 `cat` 的 Markdown；Python/Node 双栈；核心概念（cube、L1/L2/L3）要学。

**链接**：[GitHub](https://github.com/MemTensor/MemOS) · [文档](https://memos-docs.openmem.net) · [arXiv 2507.03724](https://arxiv.org/abs/2507.03724)

### D-5 ZifaMem ✅（论文 + SDK）

**定位**：AI 伴侣的**结构化记忆系统**。不是 bot 框架，是记忆层。

**结构**（简单得有点意外）：session summaries + episodic memories + consolidated user model，三层。

**实验结论**（受控，固定 LLM-as-judge 协议，四个 backbone）

| 结论 | 数字 |
|---|---|
| 相比"全量原文进上下文" | 情绪智力得分 **+11.4%**（95% CI 6.3–17.1） |
| persona 一致性 | 四个 backbone 全提升，Claude 相对 **+42%** |
| 跟 Mem0 比 | 统计上等价（±5 分内） |
| **多轮情绪上下文 vs 单轮快照** | **+39%** 净偏好（探索性） |
| **额外加"情绪状态机"** | **五个端点都没有可测收益** |

**优点**：有实验支撑，能直接用来砍需求；结构简单到可以手写。
**缺点**：只是记忆层，平台接入要自己做；单篇论文，尚未广泛复现。

**链接**：[arXiv:2607.17564](https://arxiv.org/abs/2607.17564) · [SDK](https://github.com/zifacorp/zifamem)

## 10. I 类 · 可直接抄的机制

这一节是给"自己写"准备的。前面是"用什么"，这里是"怎么写"。

---

### I-1 记忆检索的三维加权（Generative Agents）✅

来源：[Park et al. 2023](https://arxiv.org/abs/2304.03442)，[实现说明](https://github.com/agentpatterns-ai/website/blob/main/patterns/agent-design/generative-agents-memory-stream.md)。

每条记忆是一个 `ConceptNode`：时间戳 + 主谓宾三元组 + 自然语言描述 + embedding + **poignancy（重要性分）**。

检索时三维度各自归一化到 [0,1]，加权求和：

| 维度 | 信号 | 权重 |
|---|---|---|
| Recency | 距上次访问的指数衰减 | **0.5** |
| Relevance | 与当前焦点的余弦相似度 | **3.0** |
| Importance | 存储的 poignancy 分 | **2.0** |

```
score = recency×0.5 + relevance×3.0 + importance×2.0    → 取 top 30
```

**直接指出我们方案的问题**：我们的衰减公式只有 recency（`exp(-λ·days)`），**没有 relevance 和 importance 的加权组合**。单靠衰减，重要的旧事会先被忘掉；单靠相似度，日常寒暄会挤掉"那天他妈妈住院"。

---

### I-2 反思由"累计重要性"触发，不是定时 ✅

原文里反思（reflection）的触发条件是**近期观察的累计 poignancy 超过阈值**，不是每晚 02:00。

触发后：选 3 个焦点 → 检索各自关联节点 → 生成 **5 条**高层洞察（带证据链接）→ **存回观察流**成为 thought node，可再次被检索。

**这是对"每晚固定跑一次"的直接挑战**：聊得少的日子白跑（浪费 + 产生垃圾），聊得深的日子要等到第二天。

---

### I-3 反思产物要回写，不能只写日记 ✅

Generative Agents 把反思结果当普通记忆节点存回去，所以**下次还会被检索到**。我们的 `journal/` 如果只是写给人看的归档，就浪费了——应该同时进检索池。

---

### I-4 QQ 语音链路的完整配方 ✅

来源：[QQ 语音自动化链路实战](https://qqy.pw/qqbot-voice-pipeline/)（2026-02）。

```
1. 文本 → TTS（Piper，中文模型 zh_CN-huayan-medium.onnx）
2. ffmpeg 规范化：-ac 1 -ar 24000 -c:a pcm_s16le   ← 24k 单声道 16bit
3. silk-wasm encode wav → .silk
4. 以 audio 消息发送（不是当文件发）
```

**两个会让人卡一整天的坑**

1. **语音必须单独发**。和文字混发时，QQ 端会出现"消息可见但不播放"。要补文字，等 800ms 后另发一条。
2. **腾讯 SILK 的 magic bytes 以 `\x02` 开头**，直接喂 ffmpeg 会失败。识别时要先判断前缀（AstrBot 就是为这个修过 [PR #8009](https://github.com/AstrBotDevs/AstrBot/pull/8009)）。

---

### I-5 上线后怎么知道它"变味了"

[Langfuse](https://langfuse.com)（自托管）：LLM 追踪、评估、提示管理、成本统计。价值不是"看 token"，是**回放**——某次它说话很怪，能翻出当时的完整上下文，判断是记忆检索错了还是人格漂移。

---

### I-6 一个泼冷水的提醒 ✅

[《Contextual Agentic Memory is a Memo, Not True Memory》](https://arxiv.org/abs/2604.27707)批评的正是我们要做的东西：**检索式记忆本质是查找，不是真记忆**。它能按相似度泛化，但无法把经验固化成抽象规则，所以"组合性新任务"上有天花板。

对含义：**别指望文件式记忆让它"越活越聪明"**。它能给的是"记得清楚、不编造、有连续性"，"自己长出新能力"要靠改 Persona / 提示词或人工迭代。

<a id="对我们自己方案的结论"></a>
## 13. 对我们自己方案的结论

调研完之后，九个判断可以固化下来：

1. **"人格 + 记忆"的工程答案，MaiBot 给得最全。** 我们原文档的七层记忆不算错，但缺 Episode 层、缺写入/读取分离、缺图检索、缺可回滚的修正机制。这四项能从 A_Memorix 直接对照补。

2. **好感度可能是过度设计。** ZifaMem 的受控实验里，显式情绪状态机没有可测收益；qq-final 和 MaiBot 用的都是**一维标量**，而不是我们设计的四维 + 阶段 + 每日上限。

3. **"不编造共同经历"这条红线，学术界也在做。** ZifaMem 的 persona grounding、BRIDGE 的 persona consistency、H-2 的漂移检测——人格一致性**可以量化评估**，不必只靠 AGENTS.md 里的一句话。

4. **路线判断**

   | 你的偏好 | 选什么 | 代价 |
   |---|---|---|
   | 最快一个像人的 QQ bot | MaiBot | GPL，产品形态不好拆 |
   | 它真能干活（写代码/多平台） | NekroAgent | 自定义许可，情绪要自己写 |
   | 自己掌控、能上服务器 | Cortico + qq-final | pre-release，要跟版本 |
   | 桌面陪伴 | Coopanion | AGPL，上不了服务器 |
   | 留在 DSH 生态 | dsh-onebot-hub + MemOS | 跟 DSH 版本，记忆变黑盒 |

   一个收敛信号：MaiBot 的 A_Memorix 和 NekroAgent 的 Memory System **不约而同用了同一套分层**——实体 / 关系 / 段落 / episode / 向量。两个独立团队、不同语言、不同框架，得出同一个结构，这比任何单篇论文都可信。

5. **记忆方案需要改三处**（若继续自己的路线）：加 Episode 层、写入与读取分开设计、好感度降维。

6. **封号风险的主要来源不是"聊得多"，是协议端配置。** 2025-09 那批永久封禁，起因是 WebUI 默认 `0.0.0.0` + 默认 token。**只监听 127.0.0.1、改默认 token、不暴露端口**，这三条比"少说话"重要得多。

7. **如果继续 DSH 路线，记忆可以不用自己写。** MemOS 本地插件一条命令就有。取舍：**可读可控（文件）vs 省事强大（服务）**。

8. **我们的衰减公式缺两个维度。** `recency×0.5 + relevance×3.0 + importance×2.0`（各自归一化），我们只有 recency。

9. **"每晚 02:00 反思"可能不是好设计。** 累计重要性触发 + 产物回写检索池，比固定定时器更接近人。
