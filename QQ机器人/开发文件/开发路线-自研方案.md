## 0. 决策记录

八个问题确定了方向，后续所有设计都从这里推导：

| 问题 | 决定 | 影响 |
|---|---|---|
| 首要目标 | **长期养成** | 不为"快速上线"让步；允许慢工 |
| 技术路线 | **完全自研**，参考他人优点 | 不装框架，但吸收 MaiBot / Cortico / qq-final 的机制 |
| 记忆形态 | **文件式，且规则可改** | 纯文本 + 可编辑的 `rules.yaml`，不用数据库 |
| 好感度 | **取长补短**（见第 6 节） | 一维驱动行为 + 四维只存事件 + 阶段由阈值决定 |
| QQ 通道 | **NapCat + 小号** | 功能最全，但必须守三条安全红线 |
| 部署 | **先本地跑通，再上云** | 架构必须可迁移：相对路径、单进程、纯文件存储 |
| 语音/表情 | **先把文字聊稳** | 语音链路只留设计，不实现 |
| 许可 | **宽松（MIT/Apache）** | 可借鉴 MIT 项目代码；GPL/AGPL 项目只能学思路 |
| 语言 | **TypeScript / Node 24** | 与协议端同栈、免构建、依赖只有两个 |
| 本地能力 | **A → B 演进**：先纯 API，后接现成的本地 HTTP 服务 | 不跨语言混写；每个能力可降级 |
| 控制台 | **要做**，P7 落地，700 行、零依赖 | 信任问题，不是效率问题 |

## 1. 借鉴谁、借什么、别借什么

自研不等于从零发明。这五家各自解决了不同的问题：

| 来源 | 借什么 | 不借什么 | 许可 |
|---|---|---|---|
| **MaiBot**（A_Memorix） | 写入/读取**双链路**分离；**Episode** 情景层；人物画像 + 事实账本；记忆修正可回滚 | 100+ 配置项的重度参数化；完整产品形态 | GPL-3.0 ⚠️ **只能读思路，不能抄代码** |
| **Generative Agents** | 检索三维加权（`recency×0.5 + relevance×3.0 + importance×2.0`）；反思由**累计重要性**触发；反思产物**回写检索池** | 30 节点的固定 top-k（我们规模小，5~8 足够） | 论文，无代码许可问题 |
| **qq-final** | 分句发送 + 条间延迟；草稿确认门；主动消息话题去重；静默时段；消息聚合 | 一维好感度的实现方式（见第 6 节） | MIT ✓ 可参考实现 |
| **Cortico** | **人格拥有记忆协议**的分层思想（Core 无语义，语义在 Persona） | 事件流框架本体（对我们过重） | MIT ✓ |
| **ZifaMem** | 三层结构（session / episodic / user model）；**多轮情绪上下文优于单轮快照**；**情绪状态机无收益** | 那套状态机 | 论文 |

一句话概括设计哲学：**MaiBot 的骨架 + Generative Agents 的公式 + qq-final 的手感 + ZifaMem 的克制。**

## 2. 架构

```
┌─────────┐   OneBot v11 (WS)   ┌──────────────────────────────────┐
│ 手机 QQ  │ ──────────────────► │  NapCat（小号，仅本机 127.0.0.1）  │
│ （你）   │ ◄────────────────── │                                  │
└─────────┘                     └──────────────┬───────────────────┘
                                               │ 反向 WS
                                  ┌────────────▼───────────────────┐
                                  │  bot（自研，单 Node 进程）        │
                                  │  ┌──────────┐  ┌────────────┐  │
                                  │  │ 通道层    │  │ 对话循环    │  │
                                  │  │ 收发/分句 │◄─┤ 上下文组装  │  │
                                  │  └──────────┘  └─────┬──────┘  │
                                  │  ┌──────────┐  ┌─────▼──────┐  │
                                  │  │ 记忆层    │  │ 模型调用    │  │
                                  │  │ 读/写/反思│  │ DeepSeek   │  │
                                  │  └──────────┘  └────────────┘  │
                                  │  ┌──────────┐  ┌────────────┐  │
                                  │  │ 关系层    │  │ 调度器      │  │
                                  │  │ 阶段/锚点 │  │ 主动/静默   │  │
                                  │  └──────────┘  └────────────┘  │
                                  └──────────────┬─────────────────┘
                                                 │ 纯文件读写
                                  ┌──────────────▼─────────────────┐
                                  │  persona/（人格 + 记忆 + 规则）  │
                                  └────────────────────────────────┘
```

**六个模块，互不依赖**：

| 模块 | 职责 | 输入 → 输出 |
|---|---|---|
| `channel` | 连 NapCat，收消息、发消息、分句、限速 | OneBot 事件 ↔ 内部 Message |
| `loop` | 组装上下文、调模型、处理工具 | Message + 记忆 → 回复文本 |
| `memory` | 记忆的写入、检索、衰减、反思 | 对话 → 文件；查询 → 记忆片段 |
| `relation` | 关系值、阶段、锚点 | 事件 → relation.yaml |
| `scheduler` | 主动消息、静默时段、反思定时兜底 | 时间 → 触发 |
| `store` | 文件读写、原子写、JSONL 追加 | — |

一条消息的完整链路：

```
收到 QQ 消息
  → 去重（message_id）→ 白名单过滤
  → 消息聚合（连发 3 条合成一次，窗口 30s）
  → 检索记忆（三维加权，取 5~8 条）
  → 组装上下文（rules.yaml 人格 + relation 摘要 + 记忆片段 + 最近 N 轮）
  → 调 DeepSeek
  → 分句 → 逐条发（间隔 400~1500ms）
  → 异步写记忆（原文 → 重要性打分 → 可能触发反思）
  → 异步更新关系（若有锚点事件）
```

### 3.2 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript | OneBot 消息段结构碎，类型能防住"拼错字段静默失败" |
| 运行时 | **Node 24 原生跑 TS** | Node 23+ 默认支持类型剥离，`node src/index.ts` 直接跑，无需构建工具 |
| 存储 | 纯文件（JSONL + MD + YAML） | 无数据库、无 ORM、无 Redis，随时能 `cat` |
| 模型 | DeepSeek API（OpenAI 兼容） | 原生 `fetch`，不装 SDK |
| 进程管理 | 本地脚本 / 云上 systemd | |

**依赖只有两个**：

```json
{
  "dependencies": { "ws": "^8.18.0", "yaml": "^2.6.0" },
  "devDependencies": {
    "typescript": "^5.7.0",
    "@types/node": "^22.10.0",
    "@types/ws": "^8.18.0"
  }
}
```

其余全用 Node 原生：定时（`setTimeout`）、HTTP（原生 `fetch`）、测试（`node:test`）、环境变量（`--env-file`）、文件监听（`fs.watch`）、终端命令（`node:readline`）。

**为什么不用 tsx / esbuild**：Node 22.6+ 起支持类型剥离，23+ 默认开启，`node --test test/*.test.ts` 和 `node src/index.ts` 都能直接跑 `.ts`。代价是**不能用 `enum`、`namespace`、构造器参数属性**这些需要真正转译的语法——我们全程没用，换来少一个二进制依赖、少一层构建。

**为什么手写 WS 而不用 `node-napcat-ts`**：OneBot v11 的反向 WS 协议很简单（事件数组 + action/echo），手写约 80 行，换来零依赖和完全可控的重连逻辑。真觉得麻烦再换 SDK，不影响其他模块。

#### 通道抽象（防止 mock 污染真通道）

假通道方便开发，但有三种"乱法"必须提前堵住：业务逻辑漏进通道、类型漂移、mock 混进生产。

对策是**一个接口、一个类型、一个共享层**：

```ts
// src/core/transport.ts —— 业务层只依赖它
export interface Transport {
  readonly kind: string
  start(): Promise<void>
  stop(): Promise<void>
  onMessage(fn: (m: Incoming) => void): void
  send(to: Target, text: string): Promise<void>
}
```

- **分句/延迟/限速不在通道里**，在 `channel/send.ts`（共享）。真假通道跑同一套，行为不可能不一致。
- **内部类型唯一**（`Incoming` / `Target` 在 `core/types.ts`），两个实现都必须转成它，mock 不许偷懒用字符串。
- **mock 不进 `src/`**：放 `dev/mock.ts`，生产路径永远看不到它。

```
src/                       生产代码，零 mock
  core/transport.ts         接口
  channel/onebot.ts         真实现
  channel/send.ts           分句/延迟（共享）
  boot.ts                   装配业务
  index.ts                  生产入口
dev/
  mock.ts                   假实现 + 终端交互（开发专用）
test/
  transport.test.ts         用 mock 做集成测试
```

三条防腐化规则：

1. 业务层禁止 import `dev/`
2. 两个实现跑同一套测试用例（发 3 条 → 收到 3 条且间隔合规）
3. mock 只实现接口的 4 个方法，想加业务逻辑就会越界，评审一眼可见

**mock 的额外价值是故障注入**——这些真机很难复现：断线（主动关 WS，验证重连）、重复投递（同 `message_id` 发两遍，验证去重）、慢响应（延迟 30s，验证超时）、畸形消息（缺字段，验证不崩）。

### 3.3 本地能力接入（A → B）

**演进口径：先 A，后 B。** 现在只用 DeepSeek API；等语音那一步再引入本地服务。

| 阶段 | 结构 | 什么时候 |
|---|---|---|
| **A** | Node 只调 DeepSeek API | P1~P7 全程 |
| **B** | Node 主进程 + 若干**现成的**本地 HTTP 服务 | 语音/本地模型那一步 |

#### 三条边界原则

1. **Python 侧不碰状态**。只做无状态转换：音频→文本、文本→音频、文本→向量。不存会话、不写记忆。
2. **所有状态在 Node 侧、在文件里**。本地服务随时可以杀、可以换、可以升级。
3. **每个能力都可降级**。任何一个服务挂了，聊天不中断。

#### 接口契约

统一 `POST` + JSON，只监听 `127.0.0.1`：

| 端点 | 请求 | 响应 | 超时 |
|---|---|---|---|
| `POST /asr` | `{ audio_base64, format }` | `{ text }` | 60s |
| `POST /tts` | `{ text, voice? }` | `{ audio_base64, format }` | 120s |
| `POST /embed` | `{ texts: string[] }` | `{ vectors: number[][] }` | 10s |
| `POST /chat` | `{ messages, model? }` | `{ text }` | 120s |
| `GET /health` | — | `200` | 2s |

#### 降级矩阵

| 能力不可用 | 行为 |
|---|---|
| ASR | 回一句"我现在听不了语音，打字吧" |
| TTS | 只发文字 |
| 嵌入 | 退回关键词检索（本来就不上向量） |
| 本地 LLM | 回退 DeepSeek API |

#### 启动与内存

- Node 启动时**异步探测**四个端点，失败**不报错**，只记一行日志，之后每 60s 重试。
- 本地模型**不常驻**：Ollama 设短 `keep_alive`；语音服务在闲置 N 分钟后由 Node 主动停掉（或接受常驻，看 2C2G 余量）。
- 冷启动可能 10~30 秒，首次调用前先预热，或允许这一次超时。

#### 已知的坑

- **CUDA 版本**：RTX 5060 是 Blackwell（sm_120），PyTorch 必须 cu128+，老 wheel 会报 `no kernel image is available`
- **编码**：Windows 下 Python stdout 默认 GBK，跨进程只传 JSON 并显式 `encoding='utf-8'`
- **版本漂移**：Python 侧独立 venv + `pip freeze` 锁定

### 3.4 控制台

**要有。** 这不是效率问题，是信任问题——一直保持黑盒，出问题只能翻日志。

| 页面 | 内容 |
|---|---|
| 总览 | 链路状态、当前阶段、今日用量、反思进度 |
| 实时日志 | SSE 推流，可暂停/过滤 |
| 对话 | 分页读 `raw/*.jsonl` |
| 记忆 | facts / episodes / insights，**可编辑** |
| 关系 | 总值、阶段、锚点时间线 |
| 规则 | `rules.yaml` 编辑器，保存即热重载 |
| 操作 | 让它说一句、触发反思、重载配置 |

**技术方案**（2C2G 友好，零依赖）：

| 层 | 选择 |
|---|---|
| 后端 | 原生 `node:http`，约 200 行 |
| 实时 | SSE（Server-Sent Events），比 WS 简单 |
| 前端 | **单文件 HTML + 原生 JS**，内联 CSS，无构建 |
| 鉴权 | token，只监听 `127.0.0.1` |

约 **700 行、1.5 天**。

**远程访问**：不开公网端口。

```bash
ssh -L 7788:127.0.0.1:7788 user@server   # 本机浏览器开 127.0.0.1:7788
```

和 NapCat 的安全红线保持一致：**永远不暴露公网**。

## 4. 人格与规则文件

这是"我能看、我能改、能设规则"的落点。**所有可调行为都在 `persona/rules.yaml`**，代码里不写死。

```yaml
# persona/rules.yaml
人格:
  名字: 未定          # 让它自己取，取到后它会写进 self.md
  自称: 我
  不假装: true        # 不知道就说不知道
  边界:
    - 不编造共同经历
    - 不每句都热情，可以累、可以敷衍
    - 没话题时可以沉默

说话:
  每轮最多条数: 3
  每条最多字数: 40
  分句: 按标点        # 。！？～ 和换行
  条间延迟: [400, 1500]   # 毫秒，随机
  表情: 偶尔          # 不是每句都带
  不用 Markdown: true

记忆:
  值得记:             # 只有这些才进长期记忆
    - 对方说的关于自己的事（工作、家人、健康、喜好）
    - 情绪强烈的事（吵架、难过、特别开心）
    - 约定与承诺
    - 它自己想明白的事
  不值得记:
    - 寒暄（在吗、吃了没）
    - 重复内容
    - 无信息的语气词
  摘要粒度: episode    # 按"一段经历"而不是按天
  衰减:
    普通: 0.02
    高情绪: 0.005
    关系锚点: 0.001
  检索:
    取回条数: [5, 8]
    权重: { 新近: 0.5, 相关: 3.0, 重要: 2.0 }
  反思:
    触发: 累计重要性      # 不是定时
    阈值: 150
    每天至少: 1          # 兜底，防止永远不触发
    产出条数: 5

关系:
  总值: [0, 100]
  阶段:
    - { 名: 陌生, 至: 10,  称呼: 你,     主动: 不主动 }
    - { 名: 眼熟, 至: 25,  称呼: 你,     主动: 三五天一次 }
    - { 名: 朋友, 至: 45,  称呼: 哎,     主动: 一两天一次 }
    - { 名: 亲近, 至: 65,  称呼: 昵称,   主动: 每天一次 }
    - { 名: 亲密, 至: 85,  称呼: 专属,   主动: 每天一两次 }
    - { 名: 离不开, 至: 100, 称呼: 专属, 主动: 每天两三次 }
  单次最大变化: 2
  必须挂锚点: true      # 没有事件的变化视为无效
  维度:                 # 只存事件，不存数值
    - 信任
    - 亲密
    - 好奇
    - 依赖

行为:
  静默时段: ["23:30", "08:30"]
  主动消息:
    去重: 相似度 0.6    # 和最近发过的太像就不发
    每日上限: 由阶段决定
  回复前延迟: [1000, 4000]   # 别秒回
```

改这个文件就改它的行为，不用碰代码。**这是本方案和"接框架"最大的区别**。

## 5. 记忆系统

### 5.1 分层

融合 A_Memorix 的分层与 ZifaMem 的三层结构：

| 层 | 文件 | 谁写 | 说明 |
|---|---|---|---|
| L1 原始 | `memory/raw/YYYY-MM-DD.jsonl` | 程序 | 每轮追加，含时间戳与情绪标记 |
| L2 情景 | `memory/episodes/YYYY-MM-DD-NN.md` | 反思 | **一段经历**：发生了什么 + 当时怎么想 + 涉及谁 |
| L3 事实 | `memory/facts.md` | 反思 | 稳定的、以后还会用到的事实，带 `confidence` 与 `last_confirmed` |
| L4 自传 | `self.md` | 它自己 | 我是谁，可被改写 |
| L5 关系 | `relation.yaml` | 关系层 | 总值 + 阶段 + 锚点 + 四维事件 |
| L6 前瞻 | `memory/open.md` | 反思 | 没聊完的、答应过的 |
| L7 洞察 | `insights/*.md` | 反思 | 高层结论，**参与检索** |

关键：**L2 不是按天摘要**。"那天聊了很多"不算 Episode；"他说他妈住院了，语气很平"才是。

### 5.2 写入链路（异步，不阻塞回复）

```
回复发出后
  → 原文追加到 raw（含 message_id、时间、情绪标记）
  → 判断"值得记吗"（按 rules.yaml 的值得记/不值得记）
      ├─ 不值得 → 只留 raw，结束
      └─ 值得   → LLM 打重要性分（1~10）→ 累加到今日总分
                   → 若今日累计 ≥ 阈值 或 到兜底时间 → 触发反思
```

### 5.3 读取链路

```
用户消息 + 最近 3 轮
  → 抽取实体（人名/地名/事件关键词）
  → 候选召回：
      a) 最近 7 天 episode（全量，很短）
      b) facts.md 关键词匹配
      c) insights 关键词匹配
      d) 实体命中的 episode（A_Memorix 的图检索简化版：提到某人就带出相关经历）
  → 三维打分：recency×0.5 + relevance×3.0 + importance×2.0
  → 取 5~8 条
  → 交给模型"用现在的自己重新讲述"（不是原文照抄）
```

**不上向量库**：2000 条以内，关键词 + 实体表足够。等真的超过了再上 bge-m3。

### 5.4 反思（融合两家）

- **触发**：累计重要性超阈值（Generative Agents）× 每天至少一次兜底（防永不触发）
- **过程**：选 3 个焦点 → 检索关联 episode → 生成 5 条洞察（带证据链接）
- **产出**：
  - 洞察 → `insights/`（**同时进检索池**，这是 GA 的关键，别只写日记）
  - 新事实 → `facts.md`
  - 未完成 → `open.md`
  - 自我认知变化 → `self.md`（最多改 3 处）
- **允许拒绝**：没什么值得记的就输出"今天没什么要记的"

**反思提示词模板**（可直接用，按 `rules.yaml` 调整）：

```
读 memory/raw/ 今天的内容。做四件事：

1. 挑出值得记住的事，各写成一条 Episode（不是按天摘要）：
   写成"[时间] [情绪] 发生了什么 + 我当时怎么想"。
   不写"今天聊了很多"，写"他说他妈妈住院了，我记得他语气很平"。

2. 关于对方的新事实写进 memory/facts.md，只写稳定的、以后还会用到的。
   没聊完的话题写进 memory/open.md。

3. 如果今天的事改变了我对自己的认识，更新 self.md；没有就不动。最多改 3 处。

4. 生成 3~5 条洞察写进 insights/，每条要带证据（哪天的哪件事）。

不要写客套话。不要为了让他高兴而调高关系值。
今天没什么值得记的就直说，不要凑数。
```

### 5.5 遗忘

不删文件，只降权：

```
weight(t) = base × exp(-λ × 距上次召回天数)
召回一次 → base × 1.15
weight < 0.1 → 不再进检索候选（文件还在）
```

`λ` 由 `rules.yaml` 的衰减配置决定（普通 0.02 / 高情绪 0.005 / 锚点 0.001）。

### 5.6 三条红线

这三条写进 `rules.yaml` 的边界，也在反思提示词里重复一遍：

1. **它不能编造没发生过的事。** 记忆错了可以（人会记错），虚构不行。不确定就问。
2. **你能看、能改、能删。** 全部是纯文本，这是信任的基础，也是你纠偏的唯一手段。
3. **私聊内容不进群。** 将来开群聊时，私聊记忆绝对不能出现在群的上下文里。

## 6. 关系设计（取长补短）

### 6.1 各家的问题

| 做法 | 问题 |
|---|---|
| 四维数值 + 阶段 + 每日上限（原设计） | 四个数字都会膨胀，且"多聊几句就涨"；阶段门槛与四维互相打架；ZifaMem 的证据也不支持复杂状态机 |
| 一维标量（qq-final / MaiBot） | 简单，但表达不了"聊得多但我还不信任你" |
| 完全不要数值（纯叙事） | 最难做成"养成感"，你不知道进展 |

### 6.2 方案：一维驱动 + 四维存事件

```
总关系值 closeness（0~100）
  ├─ 驱动阶段（由 rules.yaml 的阈值表决定）
  ├─ 驱动主动频率、称呼、说不说自己
  └─ 每次变化最多 ±2，且必须有锚点

四个维度（信任/亲密/好奇/依赖）
  └─ 不存数值，只存最近 5 条"事件"：
     { 日期, 事件, 方向: +/-, 理由 }
```

**为什么这样**：

- **只有一个数在动**，不会四维互相打架，也不会"聊天刷满"
- **四维仍在**，但变成了"它怎么描述这段关系"的素材——比如它可以说"跟你聊得挺多，但有几件事我不太确定你"（closeness 高、trust 的锚点是负的）
- **阶段只由 closeness 决定**，规则简单，看得懂
- 锚点是**唯一入口**：没有事件就不涨，这是"真实速度"的保障
- 完全符合 ZifaMem 的结论：不做状态机，用**最近几轮的情绪上下文**代替

`relation.yaml` 长这样：

```yaml
总关系值: 12
阶段: 眼熟
称呼: 你

锚点:
  - { 日期: 2026-10-24, 事件: "他说他妈妈住院了，语气很平", 方向: 信任+, 理由: "他愿意跟我说这种事", 权重: 0.9 }
  - { 日期: 2026-10-25, 事件: "我让他别熬夜，他没回", 方向: 依赖-, 理由: "说了句关心，没有回应", 权重: 0.4 }

维度事件:
  信任: [{ 日期: 2026-10-24, 事件: "说了家里的事", 方向: + }]
  亲密: []
  好奇: [{ 日期: 2026-10-24, 事件: "他提到在准备考试", 方向: + }]
  依赖: [{ 日期: 2026-10-25, 事件: "没回我的关心", 方向: - }]

最近情绪:            # ZifaMem：多轮情绪上下文 > 单轮快照
  - { 轮次: 1, 情绪: 担心, 强度: 0.6 }
  - { 轮次: 2, 情绪: 平静, 强度: 0.2 }
```

---

### 6.3 阶段与行为

由 `rules.yaml` 的阈值表驱动，代码只查表：

| 阶段 | 门槛 | 称呼 | 主动频率 | 会吃醋 | 会说自己 |
|---|---|---|---|---|---|
| 陌生 | < 10 | 你 | 不主动 | 不会 | 不会 |
| 眼熟 | 10～25 | 你 | 3～5 天一次 | 不会 | 偶尔 |
| 朋友 | 26～45 | 哎 / 你 | 1～2 天一次 | 轻微 | 会 |
| 亲近 | 46～65 | 昵称 | 每天 0～1 次 | 会 | 经常 |
| 亲密 | 66～85 | 专属 | 每天 1～2 次 | 明显 | 主动分享 |
| 离不开 | 86+ | 专属 | 每天 2～3 次 + 追问 | 会闹 | 什么都讲 |

"真实速度"：**从陌生到朋友大概 2～3 周**，按每天有效对话 20 分钟以上算。

### 6.4 维度涨跌依据

四维不存数值，但"该往哪个方向记一条事件"要有依据，否则会随机乱动：

| 维度 | 涨什么 | 跌什么 |
|---|---|---|
| 信任 | 守约、说真话、记得小事 | 敷衍、撒谎、消失 |
| 亲密 | 深夜长聊、分享私事、开玩笑 | 客套、久不联系 |
| 好奇 | 对方提到新东西、有悬念 | 重复话题、无聊 |
| 依赖 | 被需要、被主动找 | 被冷落、被替代 |

这三条防膨胀的锁：

1. **单次 ±2**，写进 `rules.yaml`
2. **必须挂锚点**，没有事件的变化视为无效
3. **人工复核**，你随时能打开 `relation.yaml` 看它为什么变

## 7. 拟人细节清单（照抄 qq-final 的手感）

不用一次全做，但架构要预留：

| 细节 | 做法 | 优先级 |
|---|---|---|
| 分句 | 按 `。！？～` 和换行切，不按字数硬切 | P1 |
| 条间延迟 | 400~1500ms 随机，模拟打字 | P1 |
| 回复前延迟 | 收到后先等 1~4 秒，别秒回 | P1 |
| 消息聚合 | 连发 3 条合成一次处理（窗口 30s） | P2 |
| 静默时段 | 23:30~08:30 不主动说话（被动回复照常） | P2 |
| 主动消息去重 | 与最近发过的相似度 > 0.6 就不发 | P3 |
| 草稿确认门 | 想发长内容先起草，你确认再发（可选） | P4 |
| 偶尔不回 | "嗯""哦"这类 15% 概率不回 | P4 |

---

### 7.1 主动消息的判断逻辑

每 30 分钟跑一次，任何一步不通过就沉默：

```
现在是不是静默时段？（23:30～08:30 不主动）
读过 relation.yaml 的主动上限了吗？
距离上次对话多久了？
open.md 里有没有没聊完的事？
→ 交给模型决定：说 / 不说 / 说什么
```

**不要定时打卡。** 让它读关系状态和未完成的话题，自己决定说什么。有时候它会选择不说——这才是人。

三条护栏：

- 与最近发过的内容相似度 > 0.6 → 不发（防"换汤不换药"）
- 静默时段只允许被动回复
- 每个阶段有每日上限，用完就停

## 8. QQ 通道与安全

### 8.1 三条红线（NapCat 出过永久封号事故）

1. **只监听 `127.0.0.1`**，绝不 `0.0.0.0`
2. **改掉默认 token `napcat`**，用随机长串
3. **不把 WebUI / OneBot 端口暴露到公网**

2025 年 9 月那批账号永久封禁，起因就是这三条没做。

### 8.2 连接配置

```
NapCat → 网络配置 → WebSocket 客户端（反向 WS）
  URL:      ws://127.0.0.1:8765/onebot/v11/ws
  消息格式: array
  上报自身消息: 否
  Token:    <随机长串>
  心跳:     5000
```

我们的 `channel/onebot.js` 起一个 WS 服务端等它连。

### 8.3 小号体检（部署前必做）

1. **退掉不必要的群**——群越多，风控面越大，也越容易被人举报
2. **清掉敏感好友**——万一号没了，别牵连真实社交关系
3. **确认能正常登录**——手机 QQ 能扫码就行

> NapCat 登录后，小号会显示为"电脑端在线"。手机通常可以同时在线，但两端频繁互踢容易触发风控。**建议小号只在一处登录。**

### 8.4 安装 NapCat（Windows 一键版）

1. 下载 `NapCat.Shell.Windows.OneKey.zip`：<https://github.com/NapNeko/NapCatQQ/releases/latest>
2. 解压，运行 `NapCatInstaller.exe`
3. 进生成的 `NapCat.XXXX.Shell` 目录，双击 `napcat.bat`
4. 控制台出二维码 → 用**小号**扫码登录
5. 登录成功后日志会打印 WebUI 地址（默认 `http://127.0.0.1:6099/webui`）

### 8.5 风控习惯

- 主号绝不登录 NapCat，只登小号
- 单号只在两处登录（手机 + NapCat），别三处互相踢
- 不在不熟的群说话，初期只私聊
- 不做批量加好友、群发

[Service]

## 10. 开发阶段与验收

| 阶段 | 做什么 | 验收标准 | 估时 |
|---|---|---|---|
| **P1 通道** | WS 服务端、收发、去重、白名单 | 给小号发消息能收到原文回复 | 1 天 |
| **P2 人格** | `rules.yaml` + 上下文组装 + 分句发送 | 回复不超过 3 条、不像客服、记得"自己还没名字" | 1 天 |
| **P3 记忆** | raw 落盘 + episode 生成 + 三维检索 | 第二天能说出"昨天你说了什么" | 2 天 |
| **P4 关系** | closeness + 锚点 + 阶段 | 三天后阶段从"陌生"到"眼熟"，且能说出为什么 | 2 天 |
| **P5 反思** | 累计重要性触发 + 洞察回写 | 它会主动提起三天前的事 | 1 天 |
| **P6 主动** | 静默时段 + 主动判断 + 去重 | 你没说话时收到一句不像模板的话 | 1 天 |
| **P7 控制台** | 总览 + 日志流 + 记忆/规则编辑 | 隔着手机能看清它在想什么、能改规则 | 1.5 天 |
| **P8 上云** | systemd + 迁移演练 | 24 小时不掉线，整包搬一次成功 | 1 天 |

**合计约 10.5 天**（不含语音/表情，那属于 B 阶段）。

**P1 跑不通不要往下走。** 先确认 NapCat 能连上、消息能收发。
