# 记忆分档：可行性分析

> 2026-10-26
> 用户想法：分成不同档位——一定不能忘的 / 重要 / 平常 / 不是很重要 / 临时，对应不同记忆模式。

---

## 一、现有设计的问题

现在的记忆是**按「抽象层级」分**的：

```
raw → episode → insight / fact
```

`importance` 只有 1-10 一个数字，而且**完全靠模型自己给**。

**实测问题**：

1. **模型倾向都给 5-7 分**，区分度极低（`expr` 那边也是这个问题：24 条经验全是 8 分）
2. `lambdaOf()` 的三档（≥8 / ≥5 / <5）**第一档很少触发**，等于"忘得慢"那条路形同虚设
3. **"一定不能忘"这件事现在没有保障**——比如"他叫什么""他讨厌什么"，和"他今天吃了面"用同一套衰减

**用户的直觉抓到了要害**：**有些东西不是"更重要"，是"性质不同"**。

## 二、参考的三种设计

### 1. Anthropic：两层（会话 + 长期）

[t原文](https://cloud.tencent.com.cn/developer/article/2691630)

```
会话记忆（当前任务的临时状态）
    ↓ "梦境整合"（Dreaming）
长期记忆（跨会话的经验积累）
```

**核心做法**：
- 会话结束后**异步**提炼，不打断执行
- 提炼时**同时做去重和清理**（不是只往里塞）
- 判断标准："下次遇到相似任务时，知道这件事是否能明显减少试错？"

**对我们的启发**：**清理和新增是一组动作**。我们现在只有新增，没有清理。

### 2. SS13：七级 + 一个特殊档

[源码](https://gitverse.ru/githubmirror/tgstation/content/master/code/__DEFINES/memory_defines.dm)

```c
#define STORY_VALUE_KEY        -1   // 关键（不是"酷"，是"必须记住"）
#define STORY_VALUE_SHIT        0   // 很普通
#define STORY_VALUE_NONE        1   // 正常
#define STORY_VALUE_MEH         2   // 还不错
#define STORY_VALUE_OKAY        3   // 挺好
#define STORY_VALUE_AMAZING     4   // 出色，"会永远跟着你"
#define STORY_VALUE_LEGENDARY   5   // 传奇
```

**最有价值的洞察**：**`KEY` 用 `-1`，和其他档不是同一个轴**。

- `0-5` 是"这条记忆有多值得回味"（情绪强度）
- `-1` 是"这条是身份级的，必须留"（性质）

它还单独有个 flag：

```c
#define MEMORY_FLAG_NOPERSISTENCE (1<<3)   // 不该持久化的（比如临时状态）
```

**对我们的启发**：**「核心」不是「最重要的」，是「另一种东西」**。

### 3. 艾宾浩斯遗忘曲线

经典结论：**学习后 1 小时内遗忘最快**，然后放缓。

我们的实现已经近似了（`exp(-lambda*days)`），但**只有三档 lambda**（0.005 / 0.02 / 0.04）。

## 三、用户想法的评价

### ✅ 好的地方

**1. 直觉对** —— 人确实是这样记事的：
- 名字、生日、底线 → 一辈子不忘
- 承诺、大事 → 记得住
- 日常 → 记个大概
- 一次性偏好 → 很快就忘
- 今天的天气 → 明天就没

**2. 解决了「importance 不靠谱」** —— 档位比 1-10 分好判断：
- "这条要不要永远留着" → 是/否
- "这条算重要还是平常" → 二选一

**比让模型打 1-10 分可靠得多**。

**3. 便于人工干预** —— 你可以直接说"这条设成核心"，不用纠结分数。

### ⚠️ 需要想清楚的地方

**1. 「核心」由谁定？**

如果让模型自己判断"这条是核心"，它会把**每个让它印象深的话**都当核心（就像它把 24 条经验全给 8 分）。

→ **建议：核心档只能人定。**

**2. 档位会迁移吗？**

- 一条"重要"的事，过了一年还重要吗？
- 一条"平常"的事，反复提到，该升档吗？

→ **建议：只降不升**（除了人工操作）。降档可以自动，升档要人确认。

**3. 「平常」和「不是很重要」怎么分？**

这两个档位在直觉上很模糊。

→ **建议改成 4 档 + 1 个特殊**：
- **核心**（人定，不衰减）
- **重要**（衰减极慢，139 天半衰期）
- **平常**（衰减正常，35 天）
- **临时**（7 天删）
- **不存的**（噪声，压根不写）

「不是很重要」其实等于「平常但很快被淘汰」——**用衰减自动处理，不需要单独一档**。

## 四、建议的设计

### 五档 → 四档 + 一个动作

| 档位 | 存哪 | 谁定 | 衰减 | 上限 | 例子 |
|---|---|---|---|---|---|
| **核心** | `persona/core.md` | **只能人** | **不衰减** | 30 条 | 名字、底线、"不许说X" |
| **重要** | `facts.md` 的「重要」段 | 模型+人可改 | 139 天 | 无 | 约定、承诺、重大事件 |
| **平常** | `facts.md` 的「平常」段 | 模型 | 35 天 | 200 条 | 日常偏好、习惯 |
| **临时** | `memory/temp/` | 模型 | **7 天删** | 100 条 | 搜索结果、当轮事实 |
| ~~不是很重要~~ | — | — | — | — | 用 35 天衰减自动淘汰 |

### 关键设计点

**1. 核心档单独一个文件，且只能人改**

```markdown
# 我一定不能忘的

- 他叫「欲辨已妄言」，我叫他「你」
- 他讨厌被追问感受
- 他怕黑
- 我说过要记得他熬夜的事
```

**它在 prompt 里的位置**：最前面，作为**身份级约束**。

**它自己不能写这个文件**——只有你能改。这样防止它把自己觉得重要的话都塞进去。

**2. 重要 / 平常 在 facts.md 里分段**

```markdown
# 关于这个人的事实

## 重要
- 他四级坚持要考（2026-10-25，置信 0.95，公开）

## 平常
- 他什么歌都听（2026-10-25，置信 0.9，私密）
```

**3. 临时档单独目录，自动清理**

```
persona/memory/temp/2026-10-26-搜SSR.md
```

启动时扫一遍，超过 7 天的删。

**4. 降档是自动的，升档要人**

- 重要 → 平常：**一年没提到，自动降**（或者直接衰减到看不清）
- 平常 → 重要：**只能人改**
- 任何 → 核心：**只能人改**

## 六、一个更激进的想法

**要不要干脆用「保留期限」而不是「档位」？**

每条记忆带一个 `keepUntil`：

```
- 他叫我「你」（永久）
- 他四级坚持要考（永久）
- 他今天吃了面（2026-11-02 删）
- 搜索结果：SSR 是什么（2026-11-02 删）
```

**优点**：
- 比"档位"更直接（就是"留到什么时候"）
- 自动清理是显式的

**缺点**：
- 每条都要定一个日期，模型判断不来
- 人会嫌烦

**折中**：**档位定默认可留天数 + 单条可覆盖**。

## 七、还需要你拍板的

1. **核心档谁来定**（我建议：只能你改，它只能读）
2. **重要/平常 的边界**（我建议：约定、承诺、重大事件 = 重要；一次性偏好 = 平常）
3. **要不要「不是很重要」这一档**（我建议不要，用衰减代替）
4. **档位能不能自动升**（我建议不能，只能人升）
5. **临时档存几天**（我建议 7 天）
