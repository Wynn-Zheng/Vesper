## 一、先明确一个前提

现在的插件是**同进程 `import()`** 的。这意味着：

- 插件能做的，代码能做的事它都能做（它是普通模块，不是沙箱）
- `ctx` 上那些入口（net / memory / message / files）是**便利 API**，不是安全边界
- 同步死循环、内存爆掉，宿主没有任何手段拦截

所以下面所有"隔离"相关的问题，本质是同一个问题：**要隔离到什么程度。**
这个决定会影响插件作者能写什么，所以不能只由实现方拍板。

三种档位：

| 档位 | 做法 | 能防住 | 代价 |
|---|---|---|---|
| A. 现状（信任制） | 同进程 import，权限只是约定 | 只防"手滑" | 装什么插件就等于跑什么代码 |
| B. 能力收口 | 仍同进程，但 `files` 限根 + 去掉 iframe 的 token | 误读文件、面板越权 | 挡不住恶意插件 |
| C. 真隔离 | 子进程 / `node:vm` + 受限 require | 恶意插件也受限 | 插件 API 要重构，跨进程通信、性能 |

**建议：先做 B（成本低、收益明确），把 C 当成插件生态真起来之后的事。**
理由：现在插件数量是个位数、都是自己写的；先堵住"面板能调整个控制台"和
"files 能读 .env"这两个真会被利用的口子，比重构隔离模型划算。

## 二、P0：安全（✅ 两条都已修，保留分析供追溯）

### 1. panel iframe 等于完整控制台权限

**现象**：`console/plugins.js` 里 iframe 是
`sandbox="allow-scripts allow-forms allow-same-origin"`，且 `src` 上拼着
**完整控制台 token**。面板里的 JS 可以直接 `fetch('/api/plugins/uninstall')`、
改模型、导出数据 —— 和你在控制台里手动操作权限完全一样。

**影响**：装一个面板插件 = 给它整个控制台。而"面板"这个形态，插件作者往往
会引入第三方 JS（图表库之类），等于把控制台交给了第三方代码。

**方案**
- **B1（推荐）**：iframe 去掉 `allow-same-origin`（变成不透明源），
  同时**从 URL 里去掉控制台 token**；面板要调后端时走
  `postMessage` → 宿主页面代发（宿主页面有 token）→ 回传结果。
  工作量：半天。面板里能用的 API 需要列一个白名单（比如只允许 `/call`）。
- **A1**：只在文档里写"面板插件拥有完整权限，请只装信任的插件"。
  工作量：10 分钟。**不解决问题**，但至少不误导。

**建议**：B1。这是整个插件系统里唯一"用户装了别人的东西就会中招"的地方。

### 2. files 权限能越界读 `.env`

**现象**：`host.ts` 的 `safePath()` 用 `resolve(process.cwd())` 做根，
注释写着"符号链接也按真实路径算（realpath）"，但**代码里从未调用 realpath**。
在数据目录里建一个 junction 指向根外，就能读写 `persona/rules.yaml`、`.env`
（里面是 API Key）和别的插件代码。

**影响**：`files` 权限本来是想给"插件读写自己的数据"，现在等于给了数据目录全权限。

**方案**
- **B2（推荐）**：`safePath` 里 `realpathSync` 之后再比根（注意目标可能不存在，
  要 realpath 父目录）；同时把根收窄到 `data/plugins/<id>/`，
  而不是整个 cwd。工作量：2 小时。
- **A2**：删掉 `files` 权限里的 `'..'` 相关承诺，文档改成"插件可读写数据目录"。
  工作量：10 分钟。

**建议**：B2。顺带把 `files` 的根收窄到插件自己的目录 —— 这是它本来该有的语义。

## 三、P1：稳定性（用户能感觉到）

### 3. 插件同步死循环会带走整个后端

**现象**：`while(true)` 或一次性大分配，事件循环被占住 → bot 不回复、
`/api/status` 也不响应。宿主的 `try/catch` 挡不住这个。
（异步的已经用超时解决了，见「已修」。）

**影响**：一个坏插件让整个 bot"死掉"，而且看起来像网络问题。

**方案**
- **C1**：插件跑在 `worker_threads` 或子进程里，宿主用消息通信。
  这才是真隔离，但插件 API 要重写（现在插件直接 `import` 宿主模块）。
- **C2（折中）**：给插件入口套一层 `node:vm` + 受限 `require`，
  只允许它 import 白名单模块。工作量：1-2 天，能挡住大部分误用，挡不住主动作恶。
- **A**：文档写"插件崩了会拖垮整个程序"。

**建议**：先 A（诚实说明），等真的有人写复杂插件再上 C1。

### 4. 热重载不回收资源，ESM 缓存只增不减

**现象**：每次 reload 都用 `import('...?v=N')` 拿到一个新模块实例，
旧实例被闭包钉住；插件自己创建的定时器 / 全局监听不会被清理。
重载几十次后内存持续上涨。

**方案**：要求插件实现 `deactivate()`（现在它是可选的），
宿主在 unload/reload 时**必须**调用；文档里把 `deactivate` 从"可选"改成"有资源的必须"。
工作量：1 小时（宿主）+ 文档。

**建议**：做。成本很低，能避免"越用越卡"。

### 5. 退出时后端被硬杀，NapCat 留在后台

**现象**：`before-quit` 里 `backend.kill()`。Windows 上这是 `TerminateProcess`，
后端的 `SIGTERM` 清理（冲待落盘写入、`transport.stop()`）**不会执行**；
NapCat 是 detached 启动的，后端一死它继续留着。

**方案**
- 加一个仅本机可用的 `POST /api/shutdown`（token 保护），
  Electron 退出时先请求它、等 2-3 秒、再 kill。顺手在里面 stop NapCat。
  工作量：半天。
- 或者：退出时先 `transport.stop()` 由后端自己…… 但那还是要有信号通道。

**建议**：做 `/api/shutdown`。数据完整性 + 不留孤儿进程，两个都值。

### 6. 更新失败没有提示、反复重试、`app-backup-*` 从不清理

**现象**：`applyPendingUpdate` 失败只 trace，用户不知道；每次启动都新建一份
全量备份；旧 `pending.json` 会被迁移带过来，可能把刚装的新版"降级"。

**方案**：失败时在窗口顶部插一条可关闭的提示 + 清理旧 `update/` 目录 +
迁移时**排除** `update/`、`data/.pid`。工作量：半天。

**建议**：做"迁移排除 + 失败提示"两件；清理备份可以等磁盘报警了再说。

## 四、P2：正确性与体验

下面这些 2026-11 全部已修（保留出处，防止以后改回去，见文末「已修」）。
`shell` 的处理是**整条移除**，不是改白名单 —— 理由见下。

| 问题 | 现象 | 状态 |
|---|---|---|
| 插件目录名 ≠ 清单 id | 能加载，但卸载/停用永远失败 | ✅ 已修（按扫描到的真实目录删/停用，并在控制台提示） |
| 从"已安装目录本身"覆盖安装 | 先删目标再复制已删的源 → 插件消失 | ✅ 已修（重叠直接拒绝 + 先复制到临时目录再 rename） |
| `deactivate` 抛异常 | 第一次卸载/停用必失败 | ✅ 已修（只记 warning，继续卸载/写禁用标记） |
| 插件加载失败的错看不到原因 | `/list` 丢掉扫描错误 | ✅ 已修（`/list` 返回 errors，列表顶部显示） |
| 工具名不校验 | 非法名字可能让所有对话 400 | ✅ 已修（`registerTool` 校验名字正则 + parameters 形状） |
| `shell` 白名单 | `node`/`python` 等于任意代码执行；Windows 上一半命令 ENOENT 被当成成功 | ✅ 已修（**整个权限移除**） |

`shell` 的处理值得单独说：原计划是"去掉解释器类命令"，但实测发现
`echo` / `dir` / `type` / `ls` / `cat` / `grep` / `wc` / `head` / `tail` / `uniq`
在 Windows 上**都不是可执行文件**（cmd 内置或根本没有），`execFile('echo')`
直接 ENOENT —— 也就是说去掉危险项之后它基本没用了。

所以改成整条移除：`shell` 不再是合法权限名，`ctx.exec` 不存在。
声明它的旧插件仍能加载，但会在控制台看到一条说明。
插件真要跑命令，直接用自己的 `index.mjs` 调 `node:child_process` ——
宿主本来也挡不住，`shell` 只是给了个"看起来安全其实不设防"的假象。

## 五、P3：清理（有空再说）

- `probe()` 把任何 200/401 的 `/api/status` 当成"自己的后端"（端口复用时误判）
- 启动 25 秒内窗口不存在，此时再双击图标什么都不发生
- `.env` 手写解析器不支持行内注释/`export`，出错无提示
- 渲染进程崩溃/无响应没有兜底（只有 `did-fail-load`）
- `electron/package.json` 的 electron-builder 配置打不出可用包（绿色版不受影响）
- `applyPendingUpdate` 没有 `isPackaged` 门槛，开发模式下会覆盖 `electron/`

## 七、下一步（P0 已清空）

两个 P0 都修完了。如果还要继续收口，按性价比排：

1. **P1-5 退出时优雅停后端**（加 `POST /api/shutdown`，顺手停 NapCat）—— 防丢数据 + 不留孤儿进程
2. **P1-6 更新失败提示 + 迁移排除 `update/`** —— 防"更新失败无提示"和"旧 pending 降级"
3. **BUG3-19 同步死循环隔离** —— 要子进程/VM，等于重写插件 API，**建议先不做**

插件这件事的结论没变：**没有真隔离就别假装有**。现在的边界是
"挡误用、不挡恶意"，这一点必须在文档里说清，而不是靠一个假的白名单。
