# 冲突扫描

> 排查日期：2026-10-26
> 方法：读 `src/boot.ts` 的实际执行顺序、`src/**/*.ts` 里对 `persona/` 的引用、以及各模块读同一配置项的地方。
> 结论分三档：🔴 真冲突（会出问题）／🟡 隐患（边界条件下可能出问题）／🟢 查过、无冲突。

---

## 1. 配置冲突

### 1.1 🟡 `行为.私聊暂停` 与 `视觉.开启`

**涉及**：私聊暂停、看图

**触发**：`rules.行为.私聊暂停 = true` 且用户在私聊里发图。

**实际表现**：`handle()` 里私聊暂停直接 `return`（boot.ts:205），**看图根本没机会跑**。
所以"暂停时还识别图片吗"这个担心不成立——但反过来说，**开着暂停时视觉配置是死配置**。

**严重级别**：低（行为可预期，只是配置看起来能开其实开不了）

**建议**：在 `rules.yaml` 的 `行为.私聊暂停` 注释里写一句「开启时私聊的所有功能都不跑，包括看图」。或者给 `视觉` 加一条注释说明它只在非暂停场景生效。

### 1.2 🟢 `说话.每轮最多条数` / `每条最多字数`

**涉及**：分句发送、prompt 组装

**查过**：`splitBySentence(text, 每条最多字数, 每轮最多条数)` 和 `buildSystem()` 里的约束文案用的是**同一个配置对象**。
`test-integration-bugs.ts` 验证过「分句结果不超过配置条数」「每条不超过配置字数」「prompt 里写的数字和配置一致」。

**结论**：一致，无冲突。

### 1.3 🟢 `记忆.检索.取回条数` 的两段式

**涉及**：记忆检索

**查过**：配置类型是 `[number, number]`（`取回条数[0]` 用于 facts，`[1]` 用于 episodes）。`chat.ts:93` 用 `[0] ?? 6`。
如果配置写成单个数 `6`，`[0]` 会是 `undefined`，走默认 6 —— 不会崩，但**配置写了等于没写**。

**严重级别**：低（有兜底）

**建议**：`config.ts` 的 `merge` 里对数组做长度校验，长度不对就警告。

### 1.4 🟡 `表情包.开启` 与 `视觉.开启` 都读图片

**涉及**：表情包收集、看图

**查过**：`onebot.ts` 里表情包识别（`isEmojiCandidate`）和图片 URL 提取（`extractImages`）是**两套独立逻辑**，都在消息进来时跑，互不影响。
但**同一个图会同时**：进 emoji 库（如果判定是表情包）+ 被视觉模型描述（如果视觉开着）。
多花一次视觉调用的钱。

**严重级别**：低（只是多花钱）

**建议**：如果判定是表情包，可以跳过视觉识别——表情包通常不需要详细描述。

## 2. 状态共享

### 2.1 🟢 `persona/mood.yaml`

**写者**：`mood.ts` 的 `saveMood()`（唯一）
**读者**：`chat.ts`、`evaluate.ts`、`format.ts`、`preview.ts`、`proactive.ts`、`server.ts`

**查过**：单写多读，且 `saveMood` 走 `writeAtomic`。无冲突。

### 2.2 🟢 `persona/issues.json`

**写者**：`observe.ts` 的 `saveIssueStore()`（唯一）
**读者**：`server.ts`（控制台）、`boot.ts`（回复时提一句）

**查过**：单写多读。注意 `unmentionedIssues()` 有 `slice(0, 2)`，**这是有意的**（一次只提两个问题），不是 bug。

### 2.3 🟢 `persona/will.json`

**写者**：`will.ts`（唯一）
**读者**：`boot.ts`、`reflect.ts`、`proactive.ts`

**查过**：`setImpression` 会同时写 `will.json` 和 `persona/people/<id>/impression.md`（两个文件），但**都是 will.ts 一家在写**，不会互相覆盖。

### 2.4 🟢 `persona/rules.yaml`

**写者**：`server.ts`（控制台保存配置）
**读者**：`config.ts` 的 `loadRules()`

**查过**：控制台写入后，`boot.ts` 通过 `opts.getRules()` 每次重新读——**热重载生效**。
唯一隐患：如果用户在控制台保存了一个 YAML 语法错误的文件，下一次 `loadRules()` 会警告并回退默认值。**不会崩**，但配置会"突然变回默认"。

**严重级别**：低

**建议**：控制台保存前先 `YAML.parse` 校验一遍。

### 2.5 🟢 `persona/emoji/`

**写者**：`emoji/store.ts`
**读者**：`emoji/pick.ts`、`chat.ts`

**查过**：第 1 轮已经修过——按**目录绝对路径**串行化（`dirLocks`），多个 store 实例指向同一目录也不会互相覆盖索引。

### 2.6 🟡 `persona/memory/.state.json` 与 episodes

**涉及**：记忆整理（distill）、记忆检索（recall）

**查过**：`.state.json` 记「上次整理到哪」，episodes 是整理产物。
**隐患**：如果 `distill` 正在写 episodes、同时 `recall` 在读同一个目录，可能读到半个文件。
**实际**：`appendJsonl` 和 `writeAtomic` 都是原子的（第 2 轮修过），读方要么读到旧的完整版、要么读到新的完整版。**不会读到半个**。

**严重级别**：低

## 3. 顺序依赖

### 3.1 🔴 被过滤的消息仍然进了 raw 历史

**涉及**：消息过滤（`shouldDrop`）、记忆整理（`distill`）

**实际顺序**（boot.ts）：

```
1. seen 去重
2. ensurePerson 建档
3. 替换 @QQ号 → @昵称
4. appendRaw(user)          ← 所有消息都记，包括垃圾
5. schedule（防抖聚合）
6. flush → handle()
   6.1 shouldDrop → return   ← 过滤在这里
   6.2 私聊暂停 → return
   6.3 限流 → return
   6.4 退避 → return
   ...
```

**问题**：`shouldDrop` 的注释写着「广告、刷屏、纯数字这些**别进上下文**，白烧 token」，但第 4 步已经把消息写进 raw 了。
`distill` 是从 raw 里提炼的——**所以被过滤的垃圾仍然有机会进入长期记忆**。

**严重级别**：🔴 **真冲突**（注释的意图和实际行为不一致）

**修法**（两选一）：
- **A**：把 `shouldDrop` 的判断提到 `appendRaw` 之前。垃圾完全不进 raw。
- **B**：保持现状，但让 `distill` 也调一次 `shouldDrop` 过滤 raw。

**倾向 A**——更彻底，也省 raw 的存储。

### 3.2 🟢 `私聊暂停` 维护历史

**查过**：注释说「只收消息、维护历史」，实际 `appendRaw` 在第 4 步就记了，`handle()` 里的 return 只跳过回复。
**行为符合注释**。

### 3.3 🟡 `recordPlay` 在回复之后

**涉及**：表达学习、回复自评

**实际**：`judgeReply()` 是 `void`（异步不等待），完成后才 `recordPlayReviewed`。
**问题**：如果进程在这之间重启，这一条经验会丢。**不是 bug**（丢了就丢了，下次还会有）。

## 4. 额度互相踩

### 4.1 🟡 限流 + 退避 + 主动消息额度

**涉及**：限流、退避、主动消息

**查过三道门**：

1. **限流**：`allow('u:<sender>', 行为.每分钟上限)` —— 按**发送者**算，每分钟 N 次
2. **退避**：`backoff.get(scope)` —— 按**会话**算，连续 N 次没回就停一会儿
3. **主动消息额度**：`proactiveBudget('陌生')` 等 —— 按**关系阶段**算，每天 N 条

**会不会叠加到"永远不回复"？**

- 限流是**每分钟**窗口，滑过去就恢复 ✓
- 退避有**上限秒**（`行为.退避.上限秒`），到点一定恢复 ✓
- 主动额度只影响**主动**发消息，不影响**被动**回复 ✓

**结论**：不会叠加到永久静默。

**但有一个隐患**：`被 @` 会绕过退避（代码里 `if (bo && m.passive)`），**这是对的**。
不过**限流不区分是否被 @**——如果群里有人狂 @ 它，每分钟上限一满就全丢，**包括 @**。

**严重级别**：🟡（合理但与直觉不符）

**建议**：被 @ 时也绕过限流，或者用更宽松的上限。

### 4.2 🟢 群每分钟上限与个人上限

**查过**：`u:<sender>` 和 `g:<group>` 是**两个独立的桶**，不互相消耗。
一条消息会同时消耗个人和群的额度（如果两处都检查的话）——看代码，群限流在 `handle()` 里（277 行），个人在 211 行，**都会检查**，所以一条消息消耗两个额度。

**结论**：设计合理（个人防刷、群防炸）。

## 5. 上下文预算

### 5.1 🟡 六块内容叠加会不会超

**涉及**：记忆检索、表情包、看图描述、上下文摘要、自我块、关系块

**实测**（用真配置跑 `buildSystem()`）：

| 块 | 大致字数 |
|---|---|
| 基础人格（self.md） | ~200 |
| 自我块（时间/阶段/心情） | ~100 |
| 关系块 | ~80 |
| 能力清单 | ~150 |
| 记忆（facts + episodes 召回） | ~300-600 |
| 学到的应对（plays） | ~100 |
| 群成员 | ~50 |
| **prompt 小计** | **~1000-1300 字** |
| 历史（最多 6000 字符预算） | ~6000 |
| 摘要（≤400 字） | ~400 |
| 图片描述（每张 ≤120 字，最多 4 张） | ≤480 |
| 本轮输入 | ~100 |
| **总计** | **~8000-8300 字符** |

DeepSeek 的上下文是 64K token，中文约 1.5 字符/token → 8300 字符约 5500 token。
**远没到上限**。

**结论**：不会超。

**但**：`historyMessages` 的 6000 字符预算是**硬编码的默认值**，如果以后把 `上下文压缩.摘要阈值` 调大，历史会变长，**总计可能翻倍**。那时候要重新算。

**建议**：把 6000 这个预算也做成配置项，或者按「总预算减去其他块」动态算。

### 5.2 🟢 图片描述的位置

**查过**：图片描述拼在 `userContent` 末尾（`chat.ts` 里 `userContent += renderImages(notes)`）。
**不在** system prompt 里，所以不会影响 prompt 缓存。
