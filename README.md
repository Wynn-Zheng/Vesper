# QQ Bot —— 一个会自己长大的 QQ 机器人

> 它不是一个"客服机器人"。它是一个**有记忆、有情绪、有自我认知、会自己反思**的对话体，
> 通过 NapCat 接进 QQ，跑在你自己电脑上，数据全在本地。

---

## 一、它到底是什么

一句话：**一个用 LLM 驱动的、长期陪伴型的 QQ 对话体**。

和常见的 QQ 机器人（关键词回复、插件市场、指令机器人）的区别：

| | 常见 QQ 机器人 | 这个 |
|---|---|---|
| 回复来源 | 规则 / 模板 / 单轮 LLM | **单轮 LLM + 记忆召回 + 关系状态 + 情绪 + 自我认知** |
| 记忆 | 无，或简单 KV | **分层记忆**：事实 / 情节 / 洞察 / 待问 / 核心，带衰减和检索 |
| 人格 | 写在配置里，固定 | **`persona/self.md` 它自己写**，会随反思漂移 |
| 关系 | 无 | **四维关系值**（信任/亲密/好奇/依赖）+ 阶段 + 锚点 |
| 状态 | 无 | **情绪**（情绪/强度/效价/原因），会衰减、会被事件触发 |
| 主动性 | 只能被动回复 | **可以自己插话、自己刷视频、自己发说说草稿** |
| 可控性 | 改配置 | **控制台 + 申请机制 + 三段式自我页** |

它解决的问题是：**让一个 LLM 在长期对话里保持"是同一个人"**，而不是每次都像个刚认识你的客服。

## 二、核心设计哲学（先看这五条，后面所有细节都是从这推出来的）

### 1. 记忆不是存下来就行，要"能被想起来"

绝大多数"AI 记忆"的实现是：把所有对话塞进向量库，每次检索 topK。
**这个项目没走那条路**，因为实测下来它有两个硬伤：成本高（每次都要 embedding）、效果差（相似度高 ≠ 该被想起）。

这里用的是**类人记忆模型**（依据见 `docs/人脑记忆研究.md`）：

- **两种记忆分类**：`facts`（关于某人的事实）和 `episodes`（发生过的事）
- **衰减**：事实按 tier 分档衰减（`major` 139 天半衰期，`normal` 35 天），依据 Ebbinghaus 遗忘曲线
- **可及性**：`lastRecalled` 记录"上次被想起来是什么时候"，久不想就更难想
- **分档**：`major` / `normal` 二选一，**不是 1-10 打分** —— 实测模型给 importance 打分区分度极低（24 条经验全给 8 分）
- **不合并**：相似的经历各自留痕，靠 `links` 表达关系（依据 Hintzman 1986 的多痕迹模型）
- **遗忘 ≠ 删除**：`faint` 标记只影响召回排序，不删内容（依据 Bjork 的新失用理论）

**关键取舍**：**宁可少给，不给错**。`记忆.检索.最低分` 低于阈值就不返回，而不是硬塞 topK。

### 2. 人格是长出来的，不是配出来的

`persona/self.md` 是它自己写的自述，**由自我反思（每 12 小时）和记忆整理时更新**。

但它不是随便改：

- **漂移检测**：每次改都算和上一版的相似度，低于 0.45 记一条 `drift.jsonl`
- **所有权**：`frontmatter` 的 `所有权: 我写 / 它写` 决定谁能改
  - `它写`：反思可以整体改写
  - `我写`：**原文锁死，它只能往「## 它补充的」那节追加**
- **历史快照**：每次写入前留一份 `persona/self-history/*.md`，最多 60 版，能对比

**关键取舍**：**它有自己的意愿，但没有最终决定权**。想改被锁的东西只能提申请（见第五节）。

### 3. 引用、@、发言频率都要"有理由"

一个很具体的例子：引用回复。

早期实现是 `if (addressed || hasQuestion) return true` —— 结果**每条都引用**，因为配置是"必须 @"，所以每条都是 addressed。观感极其机械。

现在的判定依据**会话分析研究**（Yajing Yang, *Quote-and-Reply in WeChat*, 2025，ERIC EJ1478736）：

引用只有三类动机 —— **回不相邻的话轮** / **不引就说不清** / **要强调某一条**。

所以改成打分制（`src/loop/quote.ts`）：

```
+2 隔了≥2条  +2 多人穿插  +1 隔了>60秒
+2 对方那条很长  +5 在澄清  +2 在强调  +1 情绪强
-2 紧挨着上一条  -2 被@  -3 私聊  -3 60秒内刚引过
≥ 3 分才引用
```

**关键取舍**：**引用是功能性的，不是礼貌性的**。没有指代困难就不该引。

### 4. 它可以说"我不知道"，但不许编

`scripts/test-honesty.ts` 是一项**常驻测试**（47 条断言），专门守这条：

- prompt 里不能说"我上不了网"（它其实能调 B 站接口，只是不能搜任意网页）
- 不能假装看过视频画面（它只拿标题和简介）
- 被问到自己会什么，要照 `self.md` 的「我能做什么」说，不能临时编
- 能力诚实性检查会扫源码，发现"exec 用变量当命令"这种危险调用

### 5. 用户能观察、能调整，但不该管它的内心

这是「自我」页三段式的由来（见第六节）：

```
你设的        你说了算      不能越的线、称呼、说话方式
协商中        申请机制      名字、它自己写的规矩、它想改的
它长的        它自由        我是谁、心情、生活、学到的、问题、记忆
```

**关键取舍**：**改它的心情就不是它了**。所以心情、编的生活、在想什么，只读（最多能删）。

### 3.3 为什么控制台是单文件 HTML

`console/index.html` 有 4200+ 行，包含 HTML + CSS + JS。

**取舍**：
- **好处**：没有构建步骤，改完刷新就生效；打包时不用处理前端构建链
- **坏处**：文件大，字符串锚点编辑容易失败（这个项目踩过很多次）
- **缓解**：按页面拆出 `napcat.js` / `plugins.js` / `test.js` / `settings.js` / `members.js`

## 四、一条消息的旅程（数据流）

这是理解整个项目的关键路径。

```
1. 你在 QQ 里发「小鲸鱼 在吗」
   ↓
2. NapCat 通过 WebSocket 推给 bot（src/channel/onebot.ts）
   - 解析 CQ 码 → 纯文本 + 图片列表
   - 去重（seen Set，最多 500 条）
   - shouldHandle 判定：群开关 / 群白黑名单 / 成员白黑名单 / 必须 @ / 叫名字 / 刚聊过
     ↑ 被拒会打日志，带具体原因（rejectReason）
   ↓
3. src/boot.ts 的消息缓冲
   - 不是每条都立刻回：安静时等 5 秒看有没有补充，活跃时等 2 秒
   - 同一个人续发给 2 秒，换人 0.5 秒，被 @ 最多等 1 秒
   - 一批最多等 8 秒（批次上限）
   - 合并后当作一条处理
   ↓
4. 退避：连续决定不说话 N 次后放慢检查频率（15s → 300s）
   ↓
5. src/loop/chat.ts 组装
   ├─ system prompt = 自我块 + 阶段块 + 人物 + 关系 + 情绪 + 记忆 + 硬约束
   │   （拼装顺序见 src/loop/prompt.ts，每一项都有 why 注释）
   ├─ 历史 = session.turns 最近 6000 字符（historyMessages）
   ├─ 超阈值就 compressHistory：最早那截让模型总结成摘要
   └─ 引用判定（quote.ts 打分）
   ↓
6. 调模型（DeepSeek）
   - 有工具时进工具循环：模型返回 tool_calls → 执行 → 结果塞回 → 再调
   - 三道停止条件：模型不要工具了 / 轮数上限 / 总时长上限
   ↓
7. 回复处理
   - 分句（按标点，每轮最多 3 条，每条最多 40 字）
   - 条间随机延迟 400~1500ms，回复前延迟 1000~4000ms
   - 引用（按判定结果）
   ↓
8. 发送（src/channel/send.ts → OneBot API）
   ↓
9. 事后（异步，不阻塞下一轮）
   ├─ 自评（judge.ts）：这条回得怎么样，0-10 分
   ├─ 关系评估（relation/evaluate.ts）：这一轮有没有改变关系，写锚点+理由
   ├─ 记 raw（memory/store.ts appendRaw）：原始对话落盘
   ├─ 表情包决策（偶尔发一张）
   └─ 失败兜底：连续失败 2 次发一句「我这会儿有点卡」
   ↓
10. 定时任务（不在这条路径上）
    - 每 30 分钟：记忆整理（distill）—— 从 raw 里抽事实、情节、洞察
    - 每 12 小时：自我反思（reflect）—— 更新 self.md
    - 每 6 小时：自检（扫日志发现问题）
    - 每 30 分钟：自动整理（记忆去重、衰减）
```

## 五、申请机制（它想改自己被锁的东西）

这是"高自由度 + 可控"之间的那个平衡点。

### 设计

复用 `core.md` 那套「**给申请权、不给写入权**」的做法，推广到其它被锁字段。

```
它想改名字 / 自述 / 规矩 / 人物档案
   ↓
调 request_change(target, content, reason) 工具
   ↓
写进 persona/requests.md（人能直接读改的 markdown）
   ↓
控制台「自我 → 协商中 → 它想改的」出现，三个按钮：
   批准           只改这一次，字段还是锁着
   批准并交权     改内容 + 以后这一项它自己管（owner 切到 it）
   忽略           丢掉，同一字段 24 小时内不许再提
   ↓
批准后：apply.ts 落到对应字段 + 写一条 episode 进它的记忆
```

### 为什么批准要写进记忆

用户原话：**「改名字这种是比较重要的东西」**。

所以 `recordApproval()` 写一条 `shared` scope 的 episode（importance 6）：

```
2026-10-28｜我把名字改了：名字改成「阿鱼」
我跟主人说想改名字。
我说的是：小鲸鱼是随手取的，我最近觉得自己更像一条鱼
他批了。名字改成「阿鱼」
```

**不是操作日志** —— 它以后翻经历能想起来"我什么时候、为什么变的"。

### 防滥用

- 每个字段最多 3 条待批
- 没理由的不收
- 被忽略后 24 小时内不许再提

## 六、自我页：三段式

原来有 6 个 tab（角色卡/心事/情绪/底线/我觉得有问题/学说话），**每个 tab 里混着三种所有权**，用户改不动也看不懂。

现在按"谁说了算"重排：

```
┌─ 你设的 ──────────── 这些话是你的，它照做 ────────────┐
│ 不能越的线（core.md，只有你能改，它只能提申请）          │
│ 它怎么称呼你（按关系阶段自动变）                        │
│ 说话方式（"去设置"跳过去改）                           │
└──────────────────────────────────────────────────────┘

┌─ 协商中 ──────── 这些是它想动、等你点头的 ────────────┐
│ 它想改的（申请队列）                                   │
│ 名字                                                  │
│ 它自己写的规矩（traits，进 prompt 当约束）              │
└──────────────────────────────────────────────────────┘

┌─ 它长的 ──────── 这些是它自己积出来的，你不改 ─────────┐
│ 我是谁（可编辑，但所有权决定它能不能覆盖）              │
│   我写 → 原文锁死，它只能往「它补充的」里加               │
│ 心情、生活、学到的说话方式、发现的问题、只属于自己的记忆  │
└──────────────────────────────────────────────────────┘

┌─ 它是怎么变的 ── 看它改了什么，不是让你改 ─────────────┐
│ 人格变化：选两个版本，行级 diff（绿加红删）             │
│ 它变过几次：时间线（时间、相似度、旧→新）               │
└──────────────────────────────────────────────────────┘
```

### 「我是谁」的两种模式

这是这块最微妙的设计。

```yaml
# persona/self.md 的 frontmatter
所有权: 我写        # 或 它写
```

| 模式 | `about`（原文） | `aboutExtra`（补充区） |
|---|---|---|
| **它写**（默认） | 它整体改写 | 不用 |
| **我写** | **你写，它碰不到** | **它只能往这里追加/更新** |

切回「它写」时两段会合并（不然它下次一改写，你写的那段就没了）。

**为什么这么设计**：用户最早只想要"锁死"，但那样它就完全没自主性了。
"锚点 + 它补充"既保住了你的设定，又让它有话说。

## 七、关键取舍（做过又推翻的方案）

这一节记录**为什么不是另一种做法**，接手时最有用。

### 7.1 为什么不用向量库做记忆

- 成本：每次对话都要 embedding
- 效果：相似度高 ≠ 该被想起（"我饿了"和"我昨天很饿"相似度很高，但后者不该每次都被召回）
- **替代方案**：结构化存储 + 多因子打分（相关性 / 重要性 / 新近性 / 可及性）

### 7.2 为什么 importance 是二选一不是 1-10

实测模型打分区分度极低 —— 24 条经验全给 8 分。**二选一（major/normal）反而判断得准**。

### 7.3 为什么试聊不带工具

`previewReply` 只调 `chat(messages, llm)`，不传 tools 规格。

**原因**：`chat()` 只负责调模型，**不执行工具**；工具循环在 `generateReply` 里。
传了 spec 会拿到 `tool_calls` 却没人执行，回复反而变空白。

**代价**：试聊里问"你能看屏幕吗"它会说没有 —— 所以界面上明确写了「这里不带工具」。

### 7.4 为什么 `abilities` 不加锁

用户原话：**「适当吹牛没啥问题，只要它被问到时能承认」**。

所以不做双层，保持自动盘点（从代码和配置推），**用 `test-honesty` 守"被问时如实认错"**，而不是用锁去堵。

### 7.5 为什么人物档案不做"整段双层"

`profile.md` 是**散文**（"他答应过不再熬到后半夜……"），硬切两段读起来很怪。

**改成字段级**：
- `meta.json` 的 `name` 可锁（`nameLocked`）
- `facts.md` 每条可标 `by=me`（你确认过，它不能改）
- `profile.md` **不让你改** —— 那是它眼里的你，改了就不是"它"了

### 7.6 为什么 Electron 版要编译 TS

Electron 33 内置 Node **20.18.3**，不支持原生 type-stripping（那是 Node 22+ 的能力）。

所以打包时用 `tsc` 编译到 `build/`，`rewriteRelativeImportExtensions` 把 `./x.ts` 改写成 `./x.js`。

### 7.7 为什么后端 spawn 要带 `ELECTRON_NO_ASAR=1`

Electron 的 asar 补丁会去解析 QQ 自己的 `application.asar`，报 `Invalid package`。
关掉它，让 Node 用原生 fs。

### 7.8 为什么主动消息看「由头」不看「频率」

**反例（曾经的做法）**：关系阶段 → 每日次数表，陌生阶段 = 永不主动。

看起来合理，实际有两个问题：

1. **会死锁**：关系衰减能把人扣回陌生，陌生又不主动 → 永远冷下去
2. **不像人**：关系再近也不会每天准时打卡；关系一般也会因为看到个东西想到你而开口

**依据**：Roberts & Dunbar (2015, *Human Nature*) 跟踪 18 个月、1,291 条关系发现，
朋友联系间隔的中位数从 1 天升到 27 天，且**冷掉的关系只有 6.7% 能回到内层**——
说明"关系好自然会主动"不成立，得给每个阶段留开口的机会。

**现在的做法**：先算**由头分**（有没有具体的事想说：没做完的事、刚发生的经历、
隔太久没联系、它自己的新鲜事、情绪波动、久未提的重要事实），
关系只管"门槛多高、间隔多长、一天最多几次"。对方连续不回就收缩，直到停。

**效果**：陌生也能在"真有话要说"时开口；亲密也不会变成打卡机。

## 十一、已知限制

1. **没有向量检索** —— 靠结构化 + 打分，对"跨领域联想"这类召回不如向量库
2. **试聊不带工具** —— 想验工具要去「工具连通性」或 QQ 里试
3. **`abilities` 会自动盘点，可能夸大** —— 靠 `test-honesty` 守"被问时认错"
4. **人格漂移不可完全避免** —— 有漂移检测和快照，但拦不住长期缓慢的变化
5. **控制台单文件 4200 行** —— 编辑容易出错，靠按行改和语法检查兜底
6. **`agenttree` 在这个项目上不稳定** —— brain 拆解会跑偏（保留 6 tab），执行器 20 分钟无产出，实际靠手工
7. **打包体积 1.47 GB** —— 大头是 NapCat + QQ 本体（1.2 GB）
8. **矛盾检测有盲区** —— 只对相似度 0.45-0.9 的"灰色地带"问模型；低相似度的矛盾（「他在北京」→「他搬去上海了」）仍会是两条并存
